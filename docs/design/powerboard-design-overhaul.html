PowerBoard — Design Overhaul Plan

A first-principles path from "clean, functional web app" to a canvas tool that looks like it belongs next to Linear, Figma, and Excalidraw. What "stunning" concretely means here, the design debt in the way, a phased plan to close it — and a build brief with everything the executing agent needs to ship each phase without re-deriving decisions.

2026-07-13 · Prepared by Claude (Opus 4.8), reviewed & extended by Claude (Fable 5) · Execution checklist: tasks/todo.md · Design doctrine: playbooks/design.md · Brand kit: docs/brand/powerboard-brand.html

North star

PowerBoard should feel like a calm, precise instrument — the chrome disappears, the canvas and the user's work carry the screen, and the one place we spend the novelty budget is watching agents edit live. Depth comes from light, layering, and restraint, not decoration. One accent (a professional slate indigo), one grid, every state designed, dark mode as designed surfaces. The bar is not "better than last week" — it's best-in-class for a canvas tool.

Reference points to measure each screen against — the right comparison is the category leader, not our previous draft:

SurfaceMeasure againstWhat we're borrowing
Canvas & connectorsFigma · Excalidraw · tldrawCursor-centered zoom, snapping, marquee, weightless pan, crisp selection affordances

Principles we're holding to

60 · 30 · 10, one accent

Dominant neutral, secondary surface, exactly one accent with exactly one job: the primary action and the key live datum. Everything else is neutral. No second blue, no decorative color.

Everything on a 4 / 8 grid

Spacing from a scale (4/8/12/16/24/32/48), never arbitrary. Proximity encodes relationship. Whitespace does the work borders currently do.

Every state is designed

Empty, loading, error, offline, success — for every panel and dialog. Skeletons over spinners. A failed save fails loud (ties to the persistence P0).

Spend novelty on the canvas

The agent-live canvas is the one signature element. Everything around it stays conventional so muscle memory (⌘Z, space-pan, ⌘0) is never surprised.

Where we are — the design debt

A full inventory of apps/web/src/styles.css (3,458 lines) and App.tsx (4,668 lines) surfaced a real, coherent foundation with specific, fixable debt. The tokens exist for color; the scales for everything else do not.

Fixed Accent was scattered across ~20 hardcoded blues

--accent existed but hover / active / selected states reinvented a blue ramp inline (#1d4ed8, #93c5fd, #3b82f6, #eff6ff…), so the app read blue while the icon is violet. Now consolidated into one derived ramp — see Phase 0 and the appendix.

Debt No spacing, radius, size, or motion scale

Zero --space-*, --r-*, --dur-*, or --ease-* tokens (the existing --text-1/2 are text colors, not a type scale). Consequences visible in the file: 19 distinct border-radius values (both 99px and 999px used for pills, plus one-off compounds like 8px 8px 3px 3px), 50 ad-hoc box-shadows despite a --shadow-pop token existing, and padding/gaps as magic numbers throughout.

Debt Inter is named but never loaded

The stack is Inter, ui-sans-serif, system-ui… but no font is bundled, so Inter only renders where the OS already has it. Worse, ~65 rules use non-standard weights (620/650/690/720/760/780/820/850…) that snap to the nearest system weight — a type hierarchy that mostly isn't rendering as authored. Bundling Inter variable would technically make those weights render; we collapse them anyway (Phase 2) because seventeen distinct weights is noise, not hierarchy.

Fixed Board-content default palette leaked blue

New shapes defaulted to a blue-tinted fill (#EFF6FF) and connectors seeded to #2563EB; the .mock-* primitives painted eyebrow labels / chart bars in blue. Now neutral ink (#44403C on #F7F6F3 paper) across the renderer, schema seed presets, and export fallbacks — Phase 5. Stored JSON untouched; the themeable board accent token and demo template stay as designed.

Decisions — resolved

Previously open questions, now decided so the build agent is never blocked mid-phase. Override any of these before triggering a session; otherwise they're the spec.

Decided Board-content defaults go neutral ink

New shapes/connectors and .mock-* primitives stop seeding blue. A user designing a blue app should get blue by choice, not inheritance — and forcing brand violet into user content would repeat the same mistake in a new hue. Exact values are specified in the Phase 5 brief below. This changes only fallback rendering: elements with an explicit stored style are untouched, and no board JSON is migrated.

Decided Bundle Inter variable — yes

Self-hosted woff2 (~110 KB, one file, weights 100–900), no CDN — offline-first is non-negotiable. Single highest-ROI polish step; the current type hierarchy largely isn't rendering as authored without it.

Sequence Foundation before beauty

Phases 1–3 (tokens → type → consolidation) are unglamorous but make Phase 4's signature work fast and consistent. Order is as numbered; Phase 4 may start once Phase 1 lands if the differentiator is wanted sooner. Phases 1+2 are small enough to ship in one session; 3 deserves its own.

Build brief — instructions for the executing agent

Written for a Claude (Opus 4.8) session with no memory of this conversation. Everything needed to execute is in this section plus the files it names. Do not re-litigate the resolved decisions above; do flag evidence that one is wrong.

Session protocol

  1. Read first, in order: CLAUDE.md (project brief — the design bar and Definition of Done live there), /Users/km/Developer/playbooks/design.md in full, this document in full, then tasks/todo.md for current state.
  2. One phase per work block. Announce which phase you're executing, write its checklist into tasks/todo.md, execute, verify, commit. Never batch two phases into one commit. Exception: Phases 1+2 may share a session but still commit separately.
  3. Run the app to verify: npm run dev from the repo root (Express server on 127.0.0.1:4318, Vite web app). Check light and dark (toggle via OS or DevTools prefers-color-scheme emulation), console clean, on real surfaces: home view, an open board with elements + connectors, the inspector, dialogs.
  4. Ship gates per phase: npm run typecheck · npm run build · npm test all pass; in-browser verification done; then commit with a message naming the phase.
  5. If reality contradicts this brief (a line number moved, a token already exists, a claim is stale): trust the code, adapt minimally, and note the discrepancy in the commit body — don't improvise a different design silently.

Hard guardrails (violating any of these = stop and reassess)

  • Phases 1–3 and 6–7 are chrome-only. Touch apps/web/src/styles.css, apps/web/index.html, apps/web/src/App.tsx (presentation code), and font assets. Do not touch packages/schema, the operation model, boardService.ts, or MCP tools in any phase of this plan.
  • Never migrate or rewrite stored board JSON. Phase 5's palette change edits fallback literals in rendering/seeding code paths only.
  • No network assets. Fonts self-hosted under apps/web/public/fonts/. No Google Fonts link, no CDN.
  • Persistence P0: no localStorage writes anywhere; a failed save/backup fails loud (visible status + console error); no catch {} on write paths.
  • One accent. Every new color derives from existing tokens or the neutral ramp. If you feel the need for a second accent, the design is wrong — simplify instead.
  • Don't break muscle memory. ⌘Z/⌘⇧Z, space-pan, cursor-centered zoom, ⌘0/⌘1, marquee select must behave identically after every phase.

Shipped — the root-cause fix. The selection ring, resize handles, snap guides and marquee all live inside the scale(zoom)-transformed .canvas-plane, so a fixed "1.5px" border rendered as 6px at 400% and a blurry 0.75px at 50% — exactly the "hairlines blur or double" failure. Fix: applyCamera now publishes a live --zoom custom property on the plane, and every affordance sizes itself with calc(px / var(--zoom)) so it holds a constant screen size at any zoom. Verified live at 0.8× and 3.05×: ring = crisp ~1–1.5px accent hairline (glow dropped); the four corner handles = a rock-steady 7.98px dot each; snap guides + marquee = accent (the rose #f43f5e guide is gone — one accent color); connector midpoint handle = 8px visual dot / 16px hit target.

Also shipped: resize now works from all four corners (nw/ne/sw/se, anchor-aware — the opposite edge stays pinned, min-size clamps toward the grabbed corner) instead of bottom-right only; each handle carries an aria-label. Connectors gained a draggable midpoint handle that bends the line by writing a waypoint through the existing update_connector op (double-click straightens) — no new operation, no schema change. Gesture audit passed as-is: ⌘0=100%, ⌘1=fit (Figma-correct), wheel/pinch zoom is cursor-centered, and trackpad pan already carries native OS momentum — so no "inertial pan" system was invented.

Connector occlusion — found and fixed. A pre-existing bug surfaced during verification: .connector-layer was z-index:0 while .artboard-frame is z-index:1, so any connector (and now its midpoint handle) running over an opaque frame was hidden and un-grabbable — connectors only showed in the gaps between frames, quietly breaking intra-frame diagram edges. Raised the layer to z-index:2 (still below snap guides/marquee at 7). Verified live: the connector line now renders over the frame, hit-tests to the connector <path> on top, and the midpoint handle is the topmost element at its point (elementFromPoint returns the hit circle) — grabbable. Element selection still passes straight through the transparent layer (a click on a card body hit-tests to the element, not the SVG). The accepted trade-off: a connector's ~16px hit-path now floats over frame content, so a click landing exactly on a line near a shape can select the connector — correct for diagrams, a minor edge case for dense mockups.

Honest gap that remains. The visual craft (ring, handles, guides, zoom-crispness, handle geometry, hit-test topmost-ness) is fully verified live; the drag gestures themselves (resize-from-corner, midpoint-bend) are verified at the code + math level only — the browser harness delivers events to accessibility refs but not to raw canvas coordinates, so it can't machine-drive a pointer drag. The handlers are the standard pointer-capture pattern and the target is now confirmed topmost/grabbable, so a real drag will reach them.
