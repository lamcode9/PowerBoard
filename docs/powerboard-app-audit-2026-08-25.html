PowerBoard — app audit

2026-08-25 · measured against the production bundle, on the largest real board (817 elements, 8 artboards, 34 connectors, depth 3)

Method note. Every number here comes from the production build served over HTTP, not the Vite dev server. Dev-mode figures were 3–5× worse and entirely misleading, because StrictMode double-renders. Two candidate findings were measured and discarded as non-issues — they are listed at the bottom so nobody re-opens them.

1. The one real performance problem

Confirmed · user-visible

Every state change re-renders the entire board

App.tsx is 6,243 lines holding 61 useState hooks, with zero React.memo, zero useCallback. There is no viewport culling and no virtualisation, so all 817 elements and all 1,835 layer rows sit in the DOM at once — 7,757 nodes.

The consequence is that any state change costs a full re-render of everything:

InteractionBlocking main threadNetwork involved
Theme toggle (pure client state)89 ms — one long tasknone
Select an element~80–110 ms/selection 81 ms
Drag one element416 ms across 4 long tasks (77/107/112/120)/operations 55 ms
Typing in the inspector~53 ms per characterdebounced

The theme-toggle number is the cleanest evidence: no network, no board mutation, nothing but a re-render — and it still blocks for 89 ms. Anything over 50 ms drops input responsiveness.

Fix shape (not done — it is its own project). This is the canvas/ / panels/ / inspector/ / state/ split the brief already calls for, plus React.memo on ElementView, and virtualising the layer tree. Do not attempt it inside a release cut.

2. Correctness — fixed this session

Fixed · commit 071e7bd

Live sync broke on any non-default port

mcpEndpointUrl() derived its origin from window.location, but liveSocketUrl() sitting beside it hardcoded ws://127.0.0.1:4318. main.js honours POWERBOARD_PORT, so on any other port the HTTP API worked while live sync silently died behind an "unavailable" banner. Both now share one localServerBase() helper. Verified by serving the production bundle on 4320 — the exact case that used to fail — and confirming a clean console and a live socket.

Fixed · commit 071e7bd

A status message promised cloud saves that do not exist

On socket failure the status bar said "Live sync unavailable; cloud saves still work" — including when storage mode is local, where there is no cloud. It now says the change is saved locally, which is true.

3. Open — worth fixing, not urgent

Open

Raw Node errors are shown to the user, filesystem paths included

Roughly ten call sites do setStatus(error instanceof Error ? error.message : "…"). Opening a missing board puts this in the status bar verbatim:

ENOENT: no such file or directory, open
'/Users/km/Developer/PowerBoard/boards/board_perfaudit_tmp/board.json'

Failing loud is right and is the house rule; leaking errno strings and absolute paths into UI copy is not. These want a small mapper from error → human sentence, keeping the raw text for console.error. Left alone deliberately: ten call sites each needing a judgement call is not a release-cut change.

Open · documentation

There is a third board container, not two

tasks/todo.md documents two (sandboxed app container, unsandboxed ~/Library/Application Support). There is a third: npm run dev resolves POWERBOARD_ROOT to the repo's own boards/. That is what produced the ENOENT above, when a board placed in container two was invisible to a server reading container three.

4. Measured and discarded

The ArtboardView full-array scan. It scans all project.elements twice per artboard per render with an Array.includes inside each filter, and elementPositionInArtboard does a linear .find() per ancestor level. It looks like an obvious O(A×N×S) bug. Benchmarked against the real 817-element board: 0.141 ms per render, versus 0.031 ms for a Map-indexed rewrite. That is 0.85% of a frame. Not worth touching — the win is real and irrelevant.

Slow typing in the inspector. Real typing of 16 characters took 10.5 s, which looked catastrophic. A control run typing the same string into a plain detached <input> on the same page took 9.6 s — the cost was the automation tool, not the app. Actual app overhead is ~53 ms/char. Not a finding.

5. Health baseline

npm run typecheck clean · npm test 130 passed · no empty catch blocks on any write path · the localStorage P0 named in the brief is already fixed — api.ts migrated to IndexedDB, and only theme, pane and export preferences remain in localStorage, which is exactly what the persistence rule permits. The brief is stale on that point.
